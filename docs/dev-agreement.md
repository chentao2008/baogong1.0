# 员工报工系统开发约定

本文档是本项目后续迭代的最高优先级开发依据。任何新增页面、接口、字段或业务规则，都必须先确认是否符合本文档，再修改代码。

目标不是一次性做复杂系统，而是保证第一版可以稳定试用，并且后续能持续迭代、不把业务逻辑越改越散。

## 一、系统目标

本项目是面向纺织工厂的员工报工和工资统计系统。

第一版目标：

- 管理员维护账号、工序、当前单价和员工可报工工序。
- 员工选择日期、工序和数量提交报工。
- 系统按报工当时单价计算工资。
- 员工查询自己的历史报工和工资。
- 管理员查询自己权限范围内员工的报工和工资。

第一版优先保证：

- 权限正确。
- 工资计算正确。
- 历史数据不被静默改坏。
- 代码结构能支撑后续继续迭代。

## 二、技术边界

- 前端：H5 页面。
- 后端：Python + FastAPI。
- 数据库：PostgreSQL。
- 前端和后端必须分离开发，前端不能直接访问数据库。
- 后端负责权限校验、数据校验、工资计算和数据写入。
- 前端负责页面展示、用户输入、交互提示和调用 API。

## 三、角色和权限

### 超级权限

超级权限可以：

- 查看和维护全部账号。
- 查看和维护全部工序。
- 查看全部员工报工和工资数据。
- 按员工 + 日期整体作废某一天报工记录。
- 新增、修改、停用、物理删除账号。
- 新增、修改、停用、物理删除工序。

超级权限物理删除账号或工序时，后端必须保证不能破坏已提交报工记录和历史工资归档。

超级权限作废报工记录时，不能直接删除或改写原始报工记录，只能按员工 + 日期整体作废该员工某一天的全部报工记录。作废后，该日记录不参与工资统计，但系统必须保留原始记录和作废操作日志。

### 普通管理员

普通管理员可以：

- 查看和维护自己权限范围内的员工账号。
- 新增员工账号，新增后默认纳入自己的管理范围。
- 停用自己权限范围内的员工账号。
- 配置自己权限范围内员工的可报工工序。
- 查询自己权限范围内员工的报工和工资数据。

普通管理员不能：

- 物理删除账号。
- 物理删除工序。
- 删除、修改或作废报工记录。
- 查看或管理未分配给自己的员工。
- 新增超级权限账号。
- 越权修改其他管理员的数据。

### 员工

员工可以：

- 登录员工端。
- 提交自己的报工。
- 查询自己的历史报工和工资。

员工不能：

- 进入后台管理页面。
- 查看其他员工数据。
- 通过接口提交或查询其他员工的数据。
- 删除、修改或作废已提交报工记录。

## 四、第一版页面范围

### 统一登录页面

- 管理员和员工从同一个登录页面进入系统。
- 后端返回当前用户身份。
- 前端根据角色跳转到对应页面。

### 后台账号管理

- 新增员工账号。
- 新增管理员账号。
- 修改账号名称。
- 修改或重置密码。
- 停用账号。
- 超级权限物理删除账号。
- 配置员工可报工工序。
- 配置管理员可管理员工范围。

### 后台工序管理

- 新增工序。
- 修改工序名称。
- 修改工序当前单价。
- 停用工序。
- 超级权限物理删除工序。

### 后台数据查询

- 按员工查询。
- 按日期范围查询。
- 按月份查询。
- 按工序查询。
- 查看工资总额。
- 查看工序数量汇总。
- 查看权限范围内员工的综合统计数据。

### 员工报工

- 选择今天或过去日期。
- 选择自己被配置的启用工序。
- 填写数量。
- 后端按报工当时单价计算工资。
- 显示当日工资。
- 显示当月工资。

### 员工查询

- 查询自己的历史报工。
- 按日期范围查询。
- 按月份查询。
- 按工序查询。
- 查看数量、单价、小计金额、工资汇总。
- 查看管理员确认状态。

## 五、第一版不做什么

- 不做小程序。
- 不做订单管理。
- 不做复杂审批流。
- 不做奖金、扣款、补贴。
- 不做多级组织架构。
- 不做复杂数据看板。
- 不做导出 Excel。
- 不做月度工资锁定。
- 员工和普通管理员不能删除或修改已提交报工记录；超级权限只能按员工 + 日期整体作废，不能直接删除或改写原始报工记录。

这些功能可以作为第二版或后续版本扩展，但不能在第一版中临时插入，避免破坏核心闭环。

## 六、核心业务规则

1. 员工只能查看和提交自己的报工数据。
2. 管理员只能查看和管理被分配给自己的员工。
3. 超级权限可以查看和维护全局数据。
4. 普通管理员不能物理删除账号或工序。
5. 超级权限可以物理删除账号或工序，但不能破坏历史报工和历史工资归档。
6. 工序停用后，员工不能继续选择该工序报工。
7. 工序停用后，历史报工仍然必须可查询。
8. 账号停用后不能登录。
9. 账号停用后，历史报工仍然必须可查询。
10. 报工记录必须保存报工当时的单价。
11. 修改工序当前单价，不影响历史报工记录和历史工资。
12. 工资计算公式为：数量 × 报工记录中的单价。
13. 员工只能选择今天或过去日期报工，不能选择未来日期。
14. 同一员工同一日期一旦已有报工记录，不能再次提交或覆盖；原始报工记录不能被删除或改写。
15. 同一员工同一天同一个工序只能报一次。
16. 员工正常提交报工不需要管理员审批即可生效。
17. 管理员可以确认员工提交的报工记录。
18. 管理员确认状态只影响展示，不影响工资计算。
19. 员工端可以看到报工记录的确认状态。
20. 员工和普通管理员不能删除、修改或作废报工记录。
21. 超级权限可以按员工 + 日期整体作废某一天报工记录，但不能只作废其中一条或某一个工序。
22. 作废报工记录后，该员工该日期的报工记录不参与当日、当月和后台工资统计。
23. 作废报工记录必须保留原始报工记录、原始数量、原始单价、原始小计金额和作废操作日志。
24. 作废操作日志至少记录操作人、操作时间、员工、日期和作废原因。
25. 后端接口必须做权限校验，不能只依赖前端页面隐藏。
26. 所有工资、数量和日期校验必须在后端完成。
27. 第一版需要月度工资汇总能力，数据量小时可以实时汇总，后续可落地月度汇总表。

## 七、推荐开发顺序

后续开发不能只按页面随手加代码。每个功能必须按以下顺序推进：

1. 确认业务规则。
2. 检查现有 API 是否可以复用。
3. 设计或更新 API 文档。
4. 后端实现权限、校验、业务逻辑和数据库写入。
5. 前端调用 API，实现页面展示和交互。
6. 补充最小测试或手动验收清单。
7. 更新相关文档。

可以按页面推进开发，但每个页面内部必须先定 API 和业务规则，再写前端 UI。

## 八、后端结构约定

后端代码必须逐步从单个 `main.py` 拆分为清晰模块。

推荐结构：

```text
backend/app/
  main.py                  应用入口，只负责创建 app、挂载路由和启动事件
  api/
    auth.py                登录和当前用户
    accounts.py            账号管理
    processes.py           工序管理
    employee_reports.py    员工报工和员工查询
    admin_reports.py       管理员查询和确认
    health.py              健康检查
  schemas/
    auth.py
    accounts.py
    processes.py
    work_reports.py
  services/
    auth.py
    accounts.py
    processes.py
    work_reports.py
    permissions.py
  db/
    session.py
    init_db.py
    models.py              后续引入 ORM 时使用
```

职责边界：

- `api/` 只处理 HTTP 请求和响应，不直接堆复杂业务。
- `schemas/` 只定义请求和响应数据结构。
- `services/` 放业务规则、权限判断、工资计算和流程控制。
- `db/` 放数据库连接、建表、迁移或 ORM 模型。
- `main.py` 必须保持轻薄，不继续堆接口和 SQL。

## 九、前端结构约定

前端必须逐步从单个大 `app.js` 拆分为页面和公共能力。

推荐结构：

```text
frontend/
  index.html
  styles.css
  src/
    app.js                 路由入口和应用启动
    api.js                 所有 API 请求封装
    auth.js                登录态、角色判断、退出登录
    utils/
      date.js              日期格式和月份计算
      money.js             金额格式和工资展示
      html.js              escapeHtml 等安全输出
    pages/
      login.js
      employee-report.js
      employee-history.js
      admin-accounts.js
      admin-processes.js
      admin-query.js
```

拆分原则：

- 按页面拆文件，不按超级权限和普通管理员拆两个重复页面。
- 权限差异通过条件渲染和后端权限校验处理。
- API 调用集中放在 `api.js`，页面不直接拼接大量 fetch 逻辑。
- 日期、金额、HTML 转义等公共方法放到 `utils/`。
- 页面文件只关心本页面渲染、事件绑定和调用 API。

## 十、数据库设计原则

第一版至少需要：

- 用户表：保存管理员和员工账号。
- 工序表：保存工序名称、当前单价、启用状态。
- 员工工序配置表：保存员工可以报哪些工序。
- 管理员员工权限表：保存管理员可以管理哪些员工。
- 报工记录表：保存员工、日期、工序、数量、当时单价、小计金额。
- 报工作废日志表：保存超级权限按员工 + 日期整体作废报工记录的操作日志。
- 月度工资汇总表：后续用于保存员工每月工资汇总。

关键约束建议：

- 账号名称唯一。
- 工序名称唯一。
- 报工数量必须大于 0。
- 单价和金额不能小于 0。
- 同一员工、同一日期、同一工序不能重复报工。
- 报工记录保存当时单价和小计金额，不能只依赖工序当前单价。
- 报工记录需要支持作废状态或等价字段，用于工资统计时排除已作废记录。
- 报工作废日志必须能追溯操作人、操作时间、员工、日期和作废原因。

后续数据库结构变更应使用迁移记录管理，不建议长期依赖 `create table if not exists` 写在应用入口里。

## 十一、测试和验收底线

每次改动涉及以下内容时，必须测试：

- 登录和角色跳转。
- 员工是否只能查询自己的数据。
- 管理员是否只能查询权限范围内员工。
- 超级权限是否能查看全局数据。
- 普通管理员是否不能物理删除账号和工序。
- 改工序当前单价后，历史工资是否不变。
- 已有报工日期是否不能再次提交。
- 同一天同一个工序是否不能重复提交。
- 员工和普通管理员是否不能删除、修改或作废报工记录。
- 超级权限是否只能按员工 + 日期整体作废报工记录。
- 作废后的报工是否不参与当日、当月和后台工资统计。
- 作废后原始报工记录和操作日志是否仍然可查。
- 未来日期是否不能报工。
- 停用账号是否不能登录。
- 停用工序是否不能继续报工。
- 历史报工和工资是否仍然可查。

没有自动化测试时，也必须保留手动验收记录。

## 十二、变更纪律

- 不要为了一个页面新增页面专用 API，除非确实没有可复用业务能力。
- 不要把权限只写在前端。
- 不要在前端重新计算正式工资结果，前端只能展示后端结果或做即时预览。
- 不要在多个地方复制同一段业务判断。
- 不要让 `main.py` 和 `app.js` 继续无限变大。
- 不要在没有文档记录的情况下改变核心业务规则。
- 每次较大改动前先提交当前可回滚版本。
