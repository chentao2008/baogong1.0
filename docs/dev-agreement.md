# 员工报工系统第一版开发约定

本文档是本项目第一版的开发依据。后续使用 AI coding 开发时，应先阅读本文件，并严格按这里的边界和规则实现，不要擅自扩展复杂功能。

## 技术栈

- 前端：H5
- 后端：Python + FastAPI + ORM
- 数据库：PostgreSQL

## 角色

### 管理员

管理员可以进入后台页面，管理自己权限范围内的员工、工序配置和报工数据。

管理员账号可以被指定管理若干员工。管理员只能查看和管理被分配给自己的员工账号，不能查看其他员工的数据。

### 员工

员工登录后只能进入员工端，进行自己的报工和历史查询。员工不能查看其他员工的数据，也不能进入后台管理页面。

## 第一版页面

### 1. 统一登录页面

管理员和员工都从同一个登录页面进入系统。系统根据账号角色判断登录后的去向。

- 管理员登录后进入后台管理相关页面
- 员工登录后进入员工报工页面

### 2. 后台管理页面

管理员在此页面管理工序、工序单价、员工账号和员工可报工工序。

第一版包含：

- 新增工序
- 修改工序名称
- 修改工序当前单价
- 停用工序
- 超级权限物理删除工序
- 新增员工账号
- 停用员工账号
- 超级权限物理删除账号
- 给员工配置可报工工序
- 给管理员配置可管理的员工范围

### 3. 后台查询页面

管理员只能查询自己权限范围内员工的数据。

第一版查询维度包括：

- 按员工查询
- 按日期范围查询
- 按月份查询
- 按工序查询
- 查看某员工某阶段总工资
- 查看某员工某道工序总工作量
- 查看权限范围内员工的综合统计数据

### 4. 员工报工页面

员工登录后进入自己的报工页面。

第一版包含：

- 选择报工日期
- 选择自己被配置的工序
- 填写数量
- 系统按工序单价自动计算工资
- 显示当天报工金额
- 显示当月工资汇总

### 5. 员工查询页面

员工只能查询自己的历史报工数据和工资数据。

第一版包含：

- 按日期范围查询
- 按月份查询
- 查看工序、数量、单价、小计金额
- 查看工资汇总

## 第一版做什么

- 管理员和员工统一登录
- 按账号角色进入不同页面
- 管理员管理工序和当前单价
- 管理员管理员工账号
- 管理员给员工配置可报工工序
- 管理员配置自己可管理的员工范围
- 员工提交每日工序数量
- 系统自动计算报工工资
- 员工查看当月工资汇总
- 管理员确认员工报工记录
- 员工查看报工记录的管理员确认状态
- 建立月度工资汇总表
- 管理员查询权限范围内的报工和工资统计
- 员工查询自己的历史报工和工资数据

## 第一版不做什么

- 不做小程序
- 不做订单管理
- 不做复杂审批流；已经提交的报工记录不允许任何人再次提交或修改
- 不做奖金、扣款、补贴
- 不做多级组织架构
- 不做复杂数据看板
- 不做导出 Excel
- 不做月度工资锁定

这些功能可以作为第二版或后续版本扩展。

## 核心业务规则

1. 员工只能查看自己的数据。
2. 管理员只能查看和管理被分配给自己的员工。
3. 普通管理员不能物理删除工序，只能停用工序；超级权限可以物理删除工序。
4. 普通管理员不能物理删除账号，只能停用自己权限范围内的员工账号；超级权限可以物理删除账号。
5. 报工记录必须保存报工当时的单价。
6. 修改工序当前单价，不影响历史报工记录和历史工资。
7. 工资计算公式为：数量 × 报工记录中的单价。
8. 第一版允许员工选择今天或过去日期补填，不能选择未来日期提前报工。
9. 同一员工同一日期一旦已经有报工记录，不能再次提交、覆盖、删除或修改。
10. 员工正常提交报工不需要管理员审批即可生效。
11. 管理员有报工确认按钮，可以确认员工提交的报工记录。
12. 管理员是否确认不影响工资计算，工资仍按已提交报工记录计算。
13. 员工端可以看到报工记录的确认状态变化。
14. 员工只能选择自己被配置的启用工序。
15. 后端接口必须做权限校验，不能只依赖前端页面隐藏。
16. 第一版需要月度工资汇总表，用于保存员工每月工资汇总数据。

## 按页面开发约定

后续可以按页面逐个开发，但代码设计必须保持前后端分离，并且 API 按业务能力复用。

开发任意页面前，必须先阅读：

- `docs/dev-agreement.md`
- `docs/frontend-ui-guidelines.md`
- `docs/api-guidelines.md`

开发页面时必须遵守：

1. 严格前后端分离。
2. 先检查已有后端 API、前端组件和公共方法。
3. 已有能力必须复用，不要重复创建功能相同的 API。
4. 如果需要新增 API，先说明这个页面需要哪些接口。
5. 后端负责权限校验、数据校验、工资计算。
6. 前端只负责展示、交互和调用 API。
7. 完成后更新相关文档，记录新增 API 和复用的 API。

## 建议核心数据表

第一版至少需要：

- 用户表：保存管理员和员工账号
- 工序表：保存工序名称、当前单价、启用状态
- 员工工序配置表：保存员工可以报哪些工序
- 管理员员工权限表：保存管理员可以管理哪些员工
- 报工记录表：保存员工、日期、工序、数量、当时单价、小计金额
- 月度工资汇总表：保存员工每月工资汇总数据

后续可扩展：

- 操作日志表
- 审核记录表

## 重点风险

- 历史工资不能因为工序改单价而变化。
- 员工不能通过接口访问别人的数据。
- 管理员不能越权查看未分配给自己的员工。
- 工序和账号停用后，历史数据仍然必须可查询。
- 超级权限物理删除工序或账号时，后端必须避免破坏已提交报工记录和历史工资归档。
- 报工数量、日期和金额计算必须有后端校验。
- 管理员确认状态不能影响工资计算结果。
- 报工记录一旦提交就必须保持不可变，不能静默改动历史数据。
