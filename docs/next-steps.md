# 下一步开发路线

本文档用于指导后续迭代顺序。每次开始新功能前，先看本文件，再看：

- `docs/dev-agreement.md`
- `docs/api-guidelines.md`
- `docs/frontend-ui-guidelines.md`

## 当前状态

项目已经完成第一版试用功能的雏形：

- 统一登录页面。
- 后台账号管理。
- 后台工序管理。
- 后台数据查询。
- 员工报工。
- 员工历史查询。
- PostgreSQL 后端接口雏形。

当前主要技术债：

- 后端 `main.py` 同时包含建表、schema、SQL、业务逻辑和 API 路由。
- 前端 `app.js` 同时包含所有页面、API 调用、工具函数和交互逻辑。
- 员工端接口仍通过路径中的 `account_id` 操作数据，后续需要改为后端从登录态识别当前用户。
- 后端权限校验还不完整，不能只依赖前端隐藏按钮。
- 密码仍处于演示阶段处理方式，后续不能明文保存和返回。
- 数据库结构变更暂未使用迁移工具。
- 缺少自动化测试。

## 迭代总原则

后续不要先堆新功能。优先把系统从“能跑”整理成“能稳定迭代”。

推荐顺序：

1. 先保证有 git 回滚点。
2. 先统一文档规则。
3. 再整理后端结构。
4. 再整理前端结构。
5. 再补齐登录态和权限校验。
6. 再补核心业务测试。
7. 最后继续加新功能。

## 第一阶段：整理文档

目标：让后续开发有明确依据。

需要完成：

- 统一业务规则。
- 统一超级权限物理删除规则。
- 统一报工不可修改规则。
- 统一 API 设计方向。
- 统一前端拆分方向。
- 明确后端和前端职责边界。

验收标准：

- 新增功能前能从文档判断应该改哪个接口、哪个页面、哪个业务规则。
- 文档之间没有明显冲突。

## 第二阶段：拆分后端结构

目标：不改变现有 UI、UX 和业务逻辑，只整理代码边界。

推荐拆分：

```text
backend/app/
  main.py
  api/
    health.py
    auth.py
    accounts.py
    processes.py
    work_reports.py
  schemas/
    auth.py
    accounts.py
    processes.py
    work_reports.py
  services/
    accounts.py
    processes.py
    work_reports.py
  db/
    init_db.py
    session.py
```

第一步只做搬迁，不改业务：

- 把请求模型从 `main.py` 移到 `schemas/`。
- 把健康检查移到 `api/health.py`。
- 把账号接口移到 `api/accounts.py`。
- 把工序接口移到 `api/processes.py`。
- 把报工接口移到 `api/work_reports.py`。
- 把建表和默认数据初始化移到 `db/init_db.py`。
- `main.py` 只保留创建 app、CORS、启动事件和挂载路由。

验收标准：

- 前端页面行为不变。
- 原有接口路径不变。
- `python -m compileall backend/app` 通过。
- 后端启动后 `/health` 和 `/health/db` 正常。

## 第三阶段：拆分前端结构

目标：不改变 UI 和 UX，只降低 `app.js` 复杂度。

推荐拆分：

```text
frontend/src/
  app.js
  api.js
  auth.js
  utils/
    date.js
    money.js
    html.js
  pages/
    login.js
    employee-report.js
    employee-history.js
    admin-accounts.js
    admin-processes.js
    admin-query.js
```

第一步只做搬迁，不改页面：

- API 请求函数移到 `api.js`。
- 登录态和角色判断移到 `auth.js`。
- 日期函数移到 `utils/date.js`。
- HTML 转义移到 `utils/html.js`。
- 每个页面的渲染和事件绑定移到对应 `pages/` 文件。

验收标准：

- 页面视觉不变。
- 操作流程不变。
- 路由地址不变。
- `node --check` 或浏览器加载无语法错误。

## 第四阶段：补齐登录态和权限

目标：让后端成为权限裁判。

需要完成：

- 新增或规范 `POST /api/auth/login`。
- 新增 `GET /api/me`。
- 员工端接口从登录态识别当前员工。
- 管理员接口从登录态识别当前管理员。
- 普通管理员只能访问自己管理的员工。
- 超级权限才能物理删除账号和工序。
- 前端保存的角色信息只能用于展示，不能作为后端授权依据。

验收标准：

- 员工不能通过改 URL 或接口参数查询别人数据。
- 普通管理员不能查询未分配员工。
- 普通管理员不能物理删除账号或工序。
- 停用账号不能登录。

## 第五阶段：数据库可靠性

目标：让核心业务规则有数据库兜底。

需要确认或新增：

- 账号名称唯一约束。
- 工序名称唯一约束。
- 报工数量大于 0。
- 单价和金额不小于 0。
- 同一员工、同一日期、同一工序唯一约束。
- 报工记录保存当时单价和小计金额。
- 超级权限物理删除存在历史报工的账号或工序时，采用归档保留或拒绝删除策略。

后续建议：

- 引入 Alembic 管理数据库迁移。
- 不再长期依赖应用启动时手写 `create table if not exists`。

验收标准：

- 并发或重复提交不会写出重复报工。
- 改当前单价不会影响历史工资。
- 删除或停用不会导致历史报工查询失败。

## 第六阶段：补测试

优先测试核心业务，不追求一开始覆盖全部 UI。

后端测试优先级：

- 登录成功和失败。
- 停用账号不能登录。
- 员工只能查询自己。
- 普通管理员只能查权限范围内员工。
- 普通管理员不能物理删除。
- 超级权限删除规则。
- 未来日期不能报工。
- 同日重复报工被拒绝。
- 同日同工序重复被拒绝。
- 改工序当前单价后历史工资不变。

前端手动验收优先级：

- 登录跳转。
- 员工报工。
- 员工查询。
- 后台账号管理。
- 后台工序管理。
- 后台数据查询。
- 手机端基本可用。

## 第七阶段：继续功能迭代

完成前面阶段后，再考虑新增功能：

- 管理员确认报工记录。
- 月度工资汇总表落地。
- 更完整的后台统计。
- 操作日志。
- 数据导出。
- 更复杂的审批或工资规则。

新增功能必须遵守：

1. 先写业务规则。
2. 再写 API 文档。
3. 后端先实现权限和业务。
4. 前端再实现页面。
5. 最后补测试和更新文档。
